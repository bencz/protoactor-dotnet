# Virtual Actors Guide

A practical guide to building, configuring and operating virtual actors (grains) with Proto.Actor in this fork. It
explains how the cluster behaves under the hood, which settings matter, and the patterns that keep grains correct and
fast when the cluster scales in and out.

Behavior that differs from upstream Proto.Actor is marked **(fork)**.

## 1. Mental model

**An actor processes one message at a time.** Its state is only touched by its own message handler, so it needs no
locks. Everything that reaches an actor goes through its mailbox:

- **System messages** (`Started`, `Stop`, `Watch`, `Terminated`, supervision) have priority over user messages.
- **User messages** are processed in order, one at a time.
- **While a handler awaits, the actor does not process anything else.** The mailbox stays busy until the `Task`
  completes, unless you explicitly opt into reentrancy (see [section 8](#8-concurrency-inside-a-grain)).

**A virtual actor (grain) is an actor addressed by an identity** (`ClusterIdentity` = kind + identity string) instead
of a PID. It always conceptually exists:

- **Activation on demand.** The first request for an identity activates it on some member; later requests go to the
  same activation.
- **Location transparency.** Callers never know or care which member hosts it.
- **Passivation.** An idle grain can stop itself; the next request activates it again, possibly on another member.

**Two pieces decide where a grain lives:**

| Piece | Responsibility | Implementations |
|---|---|---|
| Cluster provider (`IClusterProvider`) | Who is in the cluster | Kubernetes, Consul, etcd, seed nodes (Redis, MongoDB, PostgreSQL), test provider |
| Identity lookup (`IIdentityLookup`) | Where each grain is | `PartitionIdentityLookup` (default, in memory), `IdentityStorageLookup` (Redis, MongoDB, PostgreSQL), `PartitionActivatorLookup` |

**Delivery is at-least-once from the caller's point of view.** A cluster request that does not get an answer within
`ActorRequestTimeout` is sent again, until the caller's cancellation token expires. Design every handler so that
receiving the same request twice is harmless (see [section 6](#6-calling-grains)).

## 2. Defining grains with protobuf

Grains are defined as protobuf services. The `Proto.Cluster.CodeGen` package turns each service into a typed client,
an abstract base class and the actor that dispatches requests.

### Project layout

Keep contracts in their own project, referenced by both callers and the members hosting the grains:

```
MyApp.Grains.Contracts/
  device_messages.proto     <- messages
  device_grain.proto        <- the service (grain) definition
  MyApp.Grains.Contracts.csproj
```

```xml
<ItemGroup>
  <PackageReference Include="Google.Protobuf" />
  <PackageReference Include="Grpc.Tools" PrivateAssets="All" />
  <PackageReference Include="Proto.Cluster.CodeGen" />
</ItemGroup>
<ItemGroup>
  <!-- Messages: C# classes generated by Grpc.Tools -->
  <Protobuf Include="device_messages.proto" />
  <Protobuf Include="device_grain.proto" />
  <!-- Grains: client, base class and actor generated by Proto.Cluster.CodeGen -->
  <ProtoGrain Include="device_grain.proto" AdditionalImportDirs="." />
</ItemGroup>
```

### Messages and service

```proto
// device_messages.proto
syntax = "proto3";
package devices;
option csharp_namespace = "MyApp.Grains.Devices";

import "google/protobuf/timestamp.proto";

message ReportReadingRequest {
  string reading_id = 1;            // lets the grain ignore a request it already applied
  double value = 2;
  google.protobuf.Timestamp measured_at = 3;
}

message DeviceStatusResponse {
  double last_value = 1;
  int64 readings = 2;
}
```

```proto
// device_grain.proto
syntax = "proto3";
package devices;
option csharp_namespace = "MyApp.Grains.Devices";

import "google/protobuf/empty.proto";
import "device_messages.proto";

service DeviceGrain {
  rpc ReportReading (ReportReadingRequest) returns (google.protobuf.Empty);
  rpc GetStatus (google.protobuf.Empty) returns (DeviceStatusResponse);
}
```

The generated kind name is `<package>.<Service>` (here `devices.DeviceGrain`).

### Contract rules

- **Every message that crosses members must be a protobuf message.** Anything else falls back to the JSON serializer,
  which writes the CLR type name into the payload: it only works between nodes running the same assemblies, is slower,
  and breaks across versions. This includes Pub/Sub payloads and messages sent to child actors on other members.
- **Register every file descriptor on every member**, in every environment (local runs included):
  `RemoteConfig.WithProtoMessages(DeviceMessagesReflection.Descriptor, ...)`.
- **Evolve contracts compatibly.** Never reuse or renumber fields, add new fields instead of changing types, and keep
  removed field numbers `reserved`. During a rolling deploy, old and new members talk to each other.
- **The order of RPCs in a service matters.** Requests carry the method index, so add new RPCs at the end and never
  reorder or remove existing ones.
- **Carry an idempotency key** (an id, a version or a timestamp) in requests that change state.
- **Use `google.protobuf.Empty`** for methods without input or output.

## 3. Implementing a grain

```csharp
public class DeviceGrain : DeviceGrainBase
{
    private readonly ClusterIdentity _identity;
    private readonly IDeviceStore _store;
    private DeviceState _state = null!;

    public DeviceGrain(IContext context, ClusterIdentity identity, IDeviceStore store) : base(context)
    {
        _identity = identity;
        _store = store;
    }

    public override async Task OnStarted()
    {
        // Load the state before any request is processed; requests wait in the mailbox meanwhile
        _state = await _store.Load(_identity.Identity, Context.CancellationToken);

        // Passivate after 10 minutes without requests
        Context.SetReceiveTimeout(TimeSpan.FromMinutes(10));
    }

    public override async Task ReportReading(ReportReadingRequest request)
    {
        // Idempotent: a resent request is ignored
        if (!_state.TryApply(request.ReadingId, request.Value, request.MeasuredAt.ToDateTime()))
        {
            return;
        }

        await _store.Save(_state, Context.CancellationToken);
    }

    public override Task<DeviceStatusResponse> GetStatus() =>
        Task.FromResult(new DeviceStatusResponse { LastValue = _state.LastValue, Readings = _state.Count });

    public override Task OnReceive()
    {
        // Non-RPC messages: timers, child replies, Pub/Sub deliveries, ReceiveTimeout
        if (Context.Message is ReceiveTimeout)
        {
            Context.Poison(Context.Self);
        }

        return Task.CompletedTask;
    }
}
```

### Errors

- **Exceptions thrown by an RPC method are caught by the generated code** and returned to the caller as a
  `GrainErrorResponse`. The client then throws `GrainException`. The grain keeps running and is not restarted.
- **Throw `GrainException` with a `Code`** for expected business errors, so callers can tell them apart:
  `throw new GrainException("device is disabled", "DEVICE_DISABLED");`
- **Do not return "success" from a catch block** to hide failures. If a decision depends on a failed dependency,
  return an explicit error or an explicit fallback that the caller understands.

### Registering the kind

```csharp
// With dependency injection: constructor parameters are resolved from the service provider,
// IContext and ClusterIdentity are supplied by the cluster
var kind = DeviceGrainActor.GetClusterKind<DeviceGrain>(serviceProvider);

// Without dependency injection
var kind = DeviceGrainActor.GetClusterKind((context, identity) => new DeviceGrain(context, identity, store));

clusterConfig = clusterConfig.WithClusterKind(kind);
```

Grains are long-lived and constructed from the root provider. **Create a scope per operation** for scoped services
(database contexts, repositories) instead of injecting them directly:

```csharp
using var scope = _scopeFactory.CreateScope();
var repository = scope.ServiceProvider.GetRequiredService<IDeviceRepository>();
```

## 4. Configuring the cluster

```csharp
var actorSystemConfig = ActorSystemConfig.Setup()
    .WithMetrics();

var remoteConfig = RemoteConfig
    .BindToAllInterfaces(advertisedHost: podIp, port: 4020)
    .WithProtoMessages(DeviceMessagesReflection.Descriptor, DeviceGrainReflection.Descriptor);

var clusterConfig = ClusterConfig
    .Setup($"devices-{environment}", new KubernetesProvider(), new PartitionIdentityLookup(new PartitionConfig
    {
        GetPidTimeout = TimeSpan.FromSeconds(15),
        RebalanceActivationsCompletionTimeout = TimeSpan.FromSeconds(15),
        ActivationRequestAttempts = 2
    }))
    .WithActorActivationTimeout(TimeSpan.FromSeconds(5))
    .WithActorRequestTimeout(TimeSpan.FromSeconds(25))
    .WithHeartbeatExpiration(TimeSpan.FromSeconds(20))
    .WithClusterKind(DeviceGrainActor.GetClusterKind<DeviceGrain>(serviceProvider));

var system = new ActorSystem(actorSystemConfig)
    .WithServiceProvider(serviceProvider)
    .WithRemote(remoteConfig)
    .WithCluster(clusterConfig);
```

### The settings that matter

| Setting | Default | What it controls | Guidance |
|---|---|---|---|
| `ActorRequestTimeout` | 5 s | How long one attempt of a cluster request waits before it is sent again | Longer than the slowest `OnStarted` plus the slowest handler. Rounded up to whole seconds, minimum 1 s **(fork)**. |
| `ActorActivationTimeout` | 5 s | How long the identity owner waits for an activator to spawn the grain | Spawning returns as soon as the actor is created; `OnStarted` does not count. Keep the default. |
| `PartitionConfig.GetPidTimeout` | 5 s | How long a caller waits for the identity owner to resolve a PID | Longer than a rebalance (`RebalanceActivationsCompletionTimeout` plus the handover), or requests fail during scale events. |
| `PartitionConfig.RebalanceActivationsCompletionTimeout` | 10 s | How long a rebalance waits for in-flight activations | At least `ActivationRequestAttempts x ActorActivationTimeout`. |
| `PartitionConfig.ActivationRequestAttempts` **(fork)** | 2 | Retries of a timed out activation request against the same member | Prevents duplicate activations when a member is slow. |
| `HeartbeatExpiration` | disabled | Blocks members whose gossip heartbeat stops | Enable (e.g. 20 s) so frozen members are removed without waiting for the provider. |
| `GossipInterval` | 300 ms | Gossip frequency | Keep the default unless measurements say otherwise. |

### Choosing an identity lookup

- **`PartitionIdentityLookup` (default, recommended).** Placements live in memory, spread over the members. No
  database, the fastest lookups, and it scales with the cluster. During a topology change, requests for unknown
  identities wait until the rebalance completes.
- **`IdentityStorageLookup`** with `RedisIdentityStorage`, `MongoIdentityStorage` or `PostgreSqlIdentityStorage`.
  Placements live in a database, which is the single source of truth during topology changes. Every lookup that misses
  the PID cache costs a database round trip, and the database becomes a dependency of every activation. Use it when you
  need that guarantee or already operate the database for this purpose.
  - Keep `maxWaitBeforeStaleLock` above `ActorActivationTimeout` plus the database latency under load.
  - Leftovers of members that are gone are removed by a single member **(fork)**; activations never expire.
- **`PartitionActivatorLookup`.** The owner is also the activator, so every topology change moves grains, and the old
  and new activation briefly run side by side. Avoid it with autoscaling or slow `OnStarted`.

### Configuration hygiene

- **Fail fast on missing settings.** If the provider, advertised host or identity lookup cannot be determined, refuse to
  start instead of silently falling back to a single-node test setup.
- **Never advertise `0.0.0.0`.** On Kubernetes, pass the pod IP (downward API `status.podIP`) as the advertised host.
- **Use one cluster name per environment**, and the same in every storage key prefix (identity storage, Pub/Sub
  subscriber store, seed node discovery), so environments sharing a database never see each other.
- **Use the same configuration in every environment.** Registering protobuf descriptors only in production, for
  example, hides serialization problems until deploy.

## 5. Hosting in ASP.NET Core and Kubernetes

### Lifecycle

Start the cluster from a hosted service, and stop it on shutdown:

```csharp
public class ClusterHostedService(ActorSystem system) : IHostedService
{
    public Task StartAsync(CancellationToken cancellationToken) => system.Cluster().StartMemberAsync();

    public Task StopAsync(CancellationToken cancellationToken) => system.Cluster().ShutdownAsync(graceful: true);
}
```

- **Order of startup:** cluster first, then everything that sends requests to grains (message consumers, background
  workers). Register the hosted services in that order.
- **Order of shutdown:** stop the inputs (consumers, HTTP traffic) before the cluster, so no new work arrives while
  grains are stopping.
- **Readiness:** report ready only after `cluster.JoinedCluster` has completed. Report not ready again as soon as
  shutdown starts.
- **Liveness:** keep it cheap and independent of the cluster, so a slow rebalance never gets the pod killed.

### Graceful shutdown budget

On `ShutdownAsync(graceful: true)` every grain is stopped and finishes the messages already queued for it, which
includes its `OnStopping`. Grains are stopped 20 at a time, waiting up to 10 seconds per group.

- Set `HostOptions.ShutdownTimeout` and the pod's `terminationGracePeriodSeconds` to at least
  `ceil(grains per pod / 20) x (typical OnStopping time, up to 10 s)` plus a few seconds to leave the cluster.
- Keep `OnStopping` short. Persist continuously instead of saving everything at the end.
- A pod killed in the middle of shutdown leaves its placements behind; storage-based lookups clean them up later.

### Autoscaling

- Every topology change triggers a rebalance of identity ownership. Use an HPA scale-down stabilization window
  (`behavior.scaleDown.stabilizationWindowSeconds`) to avoid flapping.
- Size `GetPidTimeout` and `ActorRequestTimeout` so requests survive a rebalance (see the table above).

### Kubernetes provider requirements

- The service account needs permission to get, list, watch and patch pods in the namespace.
- The remoting port must be reachable between pods, and the advertised host must be the pod IP.

## 6. Calling grains

```csharp
var status = await cluster
    .GetDeviceGrain(deviceId)
    .GetStatus(CancellationTokens.FromSeconds(10));
```

### Always pass a deadline

- **Never pass `CancellationToken.None`** (or `default`). The cluster resends an unanswered request every
  `ActorRequestTimeout` until the token expires: without a deadline, a stuck grain keeps receiving the same request
  forever and the caller never returns.
- Use `CancellationTokens.FromSeconds(n)` (cached tokens, whole seconds) or a linked token that combines the caller's
  token (HTTP `RequestAborted`, gRPC `ServerCallContext.CancellationToken`) with a deadline.
- Pick the deadline from the caller's point of view: a few seconds for interactive requests, longer for background work.

### Expect duplicates

Because unanswered requests are resent, a handler can run more than once for the same logical request:

- **Make handlers idempotent**, using an id, a version or a timestamp carried in the request.
- **Optionally add `WithClusterRequestDeduplication()`** to the grain props. It drops resends of the same request; its
  window (default 1 minute) must be longer than the callers' total timeout.

### Avoid synchronous chains

Awaiting another grain inside a handler blocks the caller grain until the callee answers:

- **Head-of-line blocking.** If many grains await the same busy grain, all of them stall, their callers time out, and
  the resends pile up in the mailboxes: load amplifies itself.
- **Deadlocks.** Grain A awaiting grain B while B awaits A blocks both until the timeouts expire.

Prefer, in this order:

1. **Fire and forget** with `Context.Send` or an RPC whose result you do not await, when the caller does not need the
   answer to continue. Make the receiver idempotent.
2. **`ReenterAfter`** when you need the answer but not exclusivity while waiting (see
   [section 8](#8-concurrency-inside-a-grain)).
3. **Pull instead of push** for aggregates: let the aggregating grain query or receive periodic summaries on its own
   timer, instead of every source grain calling it on every change.
4. **Await inside the handler** only for short, bounded calls to grains that never call you back.

### Fail open or fail closed, deliberately

When a grain call fails (timeout, deactivation, rebalance), decide explicitly what the caller does, and do the same in
every entry point (REST, gRPC, consumers). A permission check that denies in one API and allows in another is a bug.

## 7. Grain lifecycle: activation, passivation and failures

### Activation

1. The first request for an identity reaches its owner, which picks an activator member and asks it to spawn the grain.
2. The activator spawns the actor and returns its PID **immediately**; `OnStarted` has not run yet.
3. `OnStarted` runs before any request reaches the grain. Requests sent meanwhile wait in its mailbox.

Consequences:

- **A slow `OnStarted` makes requests slow, never activations.** Size `ActorRequestTimeout` for it.
- **Load state with `await` in `OnStarted`.** Do not use `ReenterAfter` there: the handler would return early and
  requests would run before the state is loaded.
- **Do not depend on slow or unreliable external services in `OnStarted`** if the grain can work without them. Load
  such data lazily and fall back gracefully.

### Failures in `OnStarted`

- **(fork)** If `OnStarted` throws, the grain is deactivated: pending and incoming requests get a `DeadLetterResponse`,
  callers retry, and the next request activates it again. Nothing restarts in the background.
- In upstream Proto.Actor the grain is restarted instead, and a slow `OnStarted` that keeps failing restarts forever.
- **Do not `Poison` yourself from `OnStarted`** to signal a failure: the poison pill waits behind the requests already
  queued, which then run against missing state. Throw instead, or set a "failed" flag that makes every handler answer
  with an error and stop the grain with `Context.Stop(Context.Self)`.

### Passivation

- Set an idle timeout with `Context.SetReceiveTimeout(...)` in `OnStarted`, and stop on `ReceiveTimeout`.
- Use `Context.Poison(Context.Self)` to finish the queued messages first, or `Context.Stop(Context.Self)` to stop right
  after the current one.
- **Messages that should not keep the grain alive** (timer ticks, internal housekeeping) must implement
  `INotInfluenceReceiveTimeout`. Otherwise a periodic timer prevents passivation forever.
- Grains that should never passivate (singletons, aggregators) simply do not set a receive timeout. Keep them few.

### Stopping

`OnStopping` runs when the grain passivates, when it is stopped explicitly, and for every grain during a graceful
shutdown of its member. Do not treat it as "this grain is gone for good": the same identity may be activated again a
moment later on another member. In particular, do not delete records that say the grain should exist (see
[section 14](#14-bringing-grains-back-after-a-deploy)).

### Duplicate activations

The cluster works hard to keep a single activation per identity, and this fork closes the known gaps (activation
request retries, stale lock waits). Still, no lookup can rule out two activations in every failure scenario (for
example a network partition). Protect persisted state with optimistic concurrency (see [section 10](#10-persisting-state)).

## 8. Concurrency inside a grain

### Never touch grain state outside a handler

- **No `async void`.** Its continuation runs outside the actor's turn, concurrently with other messages, and its
  exceptions crash the process.
- **No `Task.Run` or fire-and-forget tasks that read or write fields** of the grain.
- **Do not call `Context` from other threads.** `Context` is only valid inside the current message.

### Use `ReenterAfter` for concurrent waits

`ReenterAfter` lets the grain keep processing messages while a task runs, and runs the continuation inside the actor
once the task completes:

```csharp
public override Task OnReceive()
{
    if (Context.Message is RefreshForecast)
    {
        var deviceId = _identity.Identity; // capture values, not mutable state
        var task = _forecastClient.Get(deviceId, Context.CancellationToken);

        Context.ReenterAfter(task, completed =>
        {
            if (!completed.IsCompletedSuccessfully)
            {
                _logger.LogWarning(completed.Exception, "Forecast refresh failed for {DeviceId}", deviceId);
                return Task.CompletedTask;
            }

            _state.ApplyForecast(completed.Result); // safe: runs inside the actor
            return Task.CompletedTask;
        });
    }

    return Task.CompletedTask;
}
```

- **Check `IsCompletedSuccessfully`**, not `IsCompleted`: a faulted task is also completed, and reading `Result`
  throws inside the actor.
- **The continuation may run after other messages changed the state.** Re-validate (for example with a version or
  timestamp) before applying the result.
- **Capture copies of the data the task needs** before starting it.

### Do not share mutable objects

Messages are passed by reference between local actors. Sending a `List`, `HashSet` or an entity you keep mutating
gives two actors the same object. Send immutable messages, records with immutable collections, or copies.

## 9. Child actors

A grain can spawn ordinary actors as children:

```csharp
_writer ??= Context.Spawn(Props.FromProducer(() => new DeviceWriter(_store)));
Context.Send(_writer, new PersistSnapshot(_state.ToSnapshot()));
```

**When to use them:**

- To take slow I/O (database writes, publishing to a broker, calling external APIs) off the grain's mailbox.
- To isolate work with its own failure domain and supervision.

**What to keep in mind:**

- **Children die with the parent.** When the grain passivates, is rebalanced or restarts, its children are stopped.
  `Stop` drops the messages still queued in a child's mailbox, so flush important work before stopping: request an
  acknowledgement from the writer in `OnStopping`, or write directly.
- **Watch children you depend on** (`Context.Watch(pid)`) and reset the cached PID on `Terminated`, so it is spawned
  again on the next use.
- **Talk to the parent through its PID** (`Context.Parent`) instead of a cluster call by identity: it is cheaper and
  cannot reach another activation.
- **Bound the work.** A child that receives a full snapshot on every change grows its mailbox without limit under load.
  Coalesce instead: keep the latest dirty state in the grain and flush it on a timer.
- **Children must not mutate the parent's objects** and vice versa (see [section 8](#8-concurrency-inside-a-grain)).
- **Timers:** create them with `Context.Scheduler().SendRepeatedly(...)` / `SendOnce(...)`, keep the returned
  `CancellationTokenSource`, and cancel it in `OnStopping`.

## 10. Persisting state

- **Load in `OnStarted`, write as you go.** Do not keep important changes only in memory until `OnStopping`: a crash
  or a forced shutdown loses them.
- **Snapshot before handing off.** Convert the state into an immutable snapshot (or a serialized document) before
  sending it to a writer child or another thread.
- **Use optimistic concurrency.** Store a version (or an etag) and make every write conditional on the version you
  loaded. If a duplicate activation exists, its stale write fails instead of overwriting newer data.
- **Prefer upserts** to "read, then insert if missing", which races when two activations start at the same time.
- **Coalesce writes.** Persist the latest state on a short timer instead of writing on every message.
- **For event-sourced or snapshot-based state**, see `Proto.Persistence` (for example the Marten provider, which stores
  documents as PostgreSQL `jsonb`).

## 11. Pub/Sub

```csharp
// Subscribe the grain by identity: the subscription survives passivation and reactivation
await Cluster.Subscribe("device-alerts", Context.ClusterIdentity()!, Context.CancellationToken);

// Publish
await cluster.Publisher().Publish("device-alerts", new DeviceAlert { DeviceId = deviceId }, ct);
```

- **Subscribe grains by `ClusterIdentity`**, not by PID. A PID subscription dies with that activation; an identity
  subscription reactivates the grain when a message arrives.
- **Subscribe plain actors by PID** and unsubscribe them when they stop.
- **Payloads must be protobuf messages** (see [section 2](#2-defining-grains-with-protobuf)).
- **Choose a durable subscriber store** (`IKeyValueStore<Subscribers>`) for production, and prefix its keys with the
  cluster name and environment.
- **Topics are virtual actors too.** One topic per connection or per short-lived entity creates a lot of activations
  and store writes; prefer coarser topics and filter in the subscriber.
- **In-memory subscriber lists kept inside your own grains are lost on reactivation.** If a grain fans out to
  subscribers it tracks itself, persist that list or have subscribers renew their subscription periodically.

### Delivery semantics

Know what Pub/Sub guarantees before relying on it:

- **Publishing is acknowledged before delivery.** The topic answers the publisher as soon as it has handed the batch to
  the delivery actor of each member. A successful publish means "accepted by the topic", not "processed by every
  subscriber".
- **Pub/Sub never redelivers.** Each subscriber gets the batch with a timeout of `PubSubConfig.SubscriberTimeout`
  (default 5 s, rounded up to whole seconds), and a failed delivery is not retried; there is no dead letter queue.
  - A subscriber that is **alive but slow** still processes the batch: it is already in its mailbox, so the timeout only
    means it arrives late. A burst of 200 messages to a subscriber that needs 25 ms per message, with a 1 s timeout,
    logs 161 timeouts and still delivers all 200 messages in order.
  - A subscriber that is **stopped or unreachable** loses the batch. Unreachable PID subscribers are unsubscribed
    automatically.
  - A **virtual actor** subscriber is called with a cluster request, which is resent after every
    `ActorRequestTimeout`, so a slow one can receive the same batch more than once. Make it idempotent.
- **Subscribers that cannot be activated are skipped** and logged; delivery to the other subscribers continues
  **(fork)**.
- **Failures are only visible in the logs, and the logs are throttled.** The delivery actor logs at most 10 failures per
  second and then writes `[PubSubMemberDeliveryActor] Throttled N logs`. That line is not a limit on messages: it means
  N more deliveries failed or timed out. Usually a subscriber is too slow for the publishing rate (messages arrive
  late); if the subscriber is gone, those messages were lost. Treat it as an alert.
- **Keep subscribers fast.** A subscriber that does slow work while handling a delivery makes deliveries time out. Hand
  the work to the actor's own mailbox or to a child, and return.
- **When a message must not be lost**, do not rely on Pub/Sub alone: send it to the target grain with a request (and a
  deadline), or use a durable broker, and make the receiver idempotent.

### Batching producer

`cluster.BatchingProducer(topic)` batches messages for high-throughput publishing:

- **Errors** are handled by `BatchingProducerConfig.OnPublishingError`. The default, `PublishingErrorHandlers.RetryThenFailBatch()`
  **(fork)**, retries a failed batch 3 times with exponential backoff, then fails only that batch and keeps the producer
  running. Upstream stops the producer on the first error, so every later publish fails until it is recreated; use
  `PublishingErrorHandlers.FailBatchAndStop` if you want that behavior.
- **`MaxQueueSize`** bounds the queue; when it is full `ProduceAsync` throws `ProducerQueueFullException`. Without it the
  queue is unbounded.
- **Await the task returned by `ProduceAsync`** (or observe it) to learn whether the message was published.

## 12. Feeding grains from message brokers

- **Gate consumers on cluster readiness.** Start consuming after the member joined the cluster; until then, return
  "retry later" to the broker instead of failing.
- **Pass a deadline to every grain call** and treat a timeout as a retryable failure.
- **Acknowledge after the grain answered**, so a crash does not lose messages.
- **Expect redelivery and reordering.** Retries and rebalances reorder messages: carry an event id or timestamp and
  let the grain ignore duplicates and older events.
- **Watch prefetch and head-of-line blocking.** With a prefetch of 1, one slow grain stalls the whole queue on that
  pod. Use a higher prefetch with bounded parallelism, or partition queues by key.
- **Fanning one message out to several grains** must be idempotent per grain: a retry after a partial failure reaches
  grains that already applied it.
- **Do not drop messages on transient errors.** Retry or dead-letter them explicitly.

## 13. Real-time bridges (SignalR, WebSockets)

A common pattern is one local actor per connection that subscribes to topics and pushes updates to the client:

- **Spawn the actor once per connection** in `OnConnectedAsync` (not lazily in hub methods, which can run in
  parallel and spawn duplicates), and `Poison` it in `OnDisconnectedAsync`.
- **Bound client input** (number of subscriptions, list sizes) and authorize hub methods like any other API.
- **Give every call made while stopping a deadline**, so a disconnected client never leaves an actor hanging.
- **Renew subscriptions periodically** if the publishing side keeps them in memory.

## 14. Bringing grains back after a deploy

Grains that must be active without being requested (for example to run timers) need something to wake them after a
restart. If you keep a registry of such grains:

- **Add to the registry with an upsert** when the grain activates.
- **Remove from the registry only when the grain is really finished** (an explicit "deactivate" request, or a
  deliberate idle passivation), never in `OnStopping` unconditionally: that also runs on graceful shutdown and would
  empty the registry on every deploy.
- **Make the warm-up robust:** catch and log per-grain failures, use bounded parallelism, pass deadlines, run it on one
  member only (or make it idempotent), and mark the application ready in a `finally` block or through a readiness
  check, never only on the happy path.

## 15. Observability

- **Log Proto.Actor at `Warning` or lower**, not `Error`: request timeouts, retries, dead letters, blocked members and
  rebalances are logged as warnings and are exactly what you need when something goes wrong.
- **Use typed logging** (`[LoggerMessage]`) or message templates, not interpolated strings, and pass exceptions as the
  exception argument.
- **Enable metrics** with `ActorSystemConfig.WithMetrics()` and export them with
  `MeterProviderBuilder.AddProtoActorInstrumentation()` (package `Proto.OpenTelemetry`). Watch cluster request duration,
  timeouts and mailbox lengths.
- **Enable tracing** with `TracerProviderBuilder.AddProtoActorInstrumentation()` and `Props.WithTracing()` on the grain
  props.

## 16. Testing

- **Test grains in a real cluster**, not with a mocked `IContext`. `BaseInMemoryClusterFixture` (in
  `tests/Proto.Cluster.Tests`) starts a multi-member cluster in process with the test provider.
- **Use Proto.TestKit** for plain actors: `TestProbe` to assert messages (`ExpectNext*`), `ExpectEmptyMailbox` to
  assert that nothing else arrived, and `TestKit.AwaitConditionAsync` instead of fixed delays.
- **Cover the behaviors that break in production:**
  - a request sent twice (idempotency);
  - `OnStarted` failing (callers get an error, the next request reactivates);
  - passivation and reactivation (state is reloaded, subscriptions survive);
  - graceful shutdown (pending writes are flushed);
  - a member leaving while requests are in flight.

## 17. Review checklist

**Contracts**
- [ ] Every message crossing members is protobuf, and every descriptor is registered on every member.
- [ ] New RPCs are added at the end of the service; no field is renumbered or reused.
- [ ] State-changing requests carry an idempotency key.

**Configuration and hosting**
- [ ] `ActorRequestTimeout`, `GetPidTimeout` and `RebalanceActivationsCompletionTimeout` are sized for the slowest
      `OnStarted` and for rebalances.
- [ ] Missing cluster settings fail the startup; the advertised host is the pod IP.
- [ ] Cluster name and storage key prefixes are per environment.
- [ ] Inputs start after the cluster and stop before it; readiness follows `JoinedCluster`.
- [ ] `HostOptions.ShutdownTimeout` and `terminationGracePeriodSeconds` cover a graceful shutdown.

**Grains**
- [ ] State is loaded with `await` in `OnStarted`; no `ReenterAfter` there.
- [ ] Handlers are idempotent; optional `WithClusterRequestDeduplication()`.
- [ ] No `async void`, no state access from other threads, no shared mutable objects.
- [ ] `ReenterAfter` continuations check `IsCompletedSuccessfully` and re-validate state.
- [ ] Timer messages implement `INotInfluenceReceiveTimeout`; timers are cancelled in `OnStopping`.
- [ ] Persisted writes are conditional (optimistic concurrency) and coalesced.

**Callers**
- [ ] Every grain call has a deadline; no `CancellationToken.None`.
- [ ] No awaited cycles between grains; no hot grain awaited by many others on every change.
- [ ] Failure handling (allow or deny) is the same in every entry point.

**Pub/Sub**
- [ ] Messages that must not be lost do not depend on Pub/Sub alone.
- [ ] Subscribers hand slow work off instead of doing it while handling a delivery.
- [ ] `[PubSubMemberDeliveryActor] Throttled N logs` is monitored as a delivery failure alert.

**Operations**
- [ ] Proto.Actor logs at `Warning`, metrics and tracing are enabled.
- [ ] Cluster-level tests cover duplicates, start failures, passivation and shutdown.
